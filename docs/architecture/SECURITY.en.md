# Security — English overview

> English navigation companion; the Chinese document is the canonical current specification.

Status: current. Updated: 2026-10-24.

See [SECURITY.md](SECURITY.md) for the complete current document. This overview does not define a second rule set.

The core portal/admin retain server authentication. Sign-in is one login shared by portal, forum and console. A GitHub user signing in for the first time must be an active member of `CONSOLE_ORG` to register; after that, membership is decided on the site, so a known account whose site role is recorded signs in without an organization check, and only an account whose site role is "not a member" is refused. Every failure redirects to the unified sign-in page, `/signin?signin=<reason>&return_to=<same-origin path>`, with `not_member`, `invite_pending`, `cancelled`, `failed` or `account_disabled`. Non-members and pending invitees get no session (audited as `auth.signin_denied`, and the app's grant is revoked on a best-effort basis); GitHub errors are reported as `failed` and are never treated as "not a member". When GitHub rejects the token stored in a session with a 401 (this happens only where the user's own token is used: GitHub pages without a GitHub App, the one-time role fill of a backfilled account, `/api/me/orgs`) (revoked by the user, or pushed out by the ten-token limit per user and app), the server deletes the session, clears `sid` and answers 401 `session_expired` (audited as `auth.session_rejected`, #164); `/auth/me` answers `{ signed_in: false, session_expired: true }`. A rejected GitHub App token answers 503 `github_connection_failed` and keeps the session. The invite-link path uses the GitHub App, or the link creator's stored token when no App is configured, and handles upstream errors itself, so it never ends a visitor's session. A real GitHub sign-in on a local preview was recorded on 2026-09-25; current environment acceptance must be checked against the corresponding release records. Feedback summaries and admin replies are readable anonymously through `GET /api/feedback/public`, so feedback text is treated as public; résumé submissions have no anonymous read endpoint; console reads require the corresponding application capabilities. The adopted Nuxt/TuffEx forum uses the same site-wide login (the upstream mock identity picker remains only in the upstream verification runs and the local sample preview) and uses the core forum backend for authorization and persistence; the local mock picker never grants server-side privileges. Legacy forum APIs return 410 and the old forum database is not opened. The production and preview stacks must stay fully isolated (directory, compose project, ports, volumes, secrets, domains) with host-only cookies, and runtime `.env` secrets are injected by CI/CD only — repository templates keep secret fields empty. Production rollout and operational verification require separate authorization and evidence.

Since #262 (owner decisions of 2026-10-23) the sign-in page also offers email (a 6-digit code, or a password set on the account page) and, once its credentials are configured, Google. A first GitHub sign-in registers organization members only; a first email or Google sign-in creates an account only with a valid invite code, managed in the console under `accounts.invites.manage`. Codes are stored as HMACs, expire after 10 minutes and allow five wrong tries; sending is limited per inbox and per IP in the database. Passwords need at least 8 characters with no case, digit or symbol rules (owner decision of 2026-10-23; it was 15 before), and are bcrypt-hashed; wrong email, missing password and wrong password give the same answer. Google sign-in uses PKCE, state and nonce, verifies the ID token against Google's keys and never merges accounts by email. Email and Google sessions hold no GitHub token; their permissions are the account's like everyone else's. Without a GitHub App the console's GitHub pages answer 409 `github_not_connected` for them, and `/api/me/orgs` still answers 403 `github_session_required`. Since #273 a forgotten password is reset from the sign-in page with an emailed code (`POST /auth/email/reset`, the same challenge and limits as code sign-in, never registering), and where the site can send mail an account without an email sign-in method is sent to `/bind-email` after GitHub or Google sign-in and before approving an external app or a device; the other endpoints stay open to such a session, so the bind page is guidance rather than a permission gate. Residual risk: if mail is configured but delivery keeps failing, such a person cannot get a code and stays on the bind page with only sign-out; like a password change on the account page, a reset does not end existing sessions, so someone who already signed in to the account is not signed out by it and the account has to be disabled in the console. Since #280 every account also needs a real name and a grade, whether or not the site can send mail: the same gate (`lib/email-gate.ts`, email first) sends such an account to `/complete-profile` after sign-in and before approving an external app or a device (403 `profile_required`; denying is never blocked), email registration asks for both when it would create an account (400 `real_info_required`, without spending the code or the invite), the owner fills them once through `POST /api/identity/real-info`, and afterwards only a `users.manage` holder can change them in the console. The grade is a dropdown from first to fourth year and is stored as an enrollment year, so it moves up every September 1 (Beijing time). The real name is returned only to the account itself and to `users.manage` holders; the forum, the ladder, the contest site, OIDC claims and the GitLab sync never read it, and activity records keep only whether a name exists or changed.

Permissions come from the site account only (#262 delivery 4, owner 2026-10-23: GitHub permissions are to be let go, and more forges than GitHub may follow). Each account records its membership and site role (`users.org_state`, `users.org_role`): admin (提督), member (舰员) or not a member. Whatever the sign-in method, capabilities follow the site role and titles; the user's GitHub organization role is not consulted. Invite registrants are members; organization members are recorded as members on their first GitHub sign-in, owners included (an owner becomes admin only while the site has no admin at all, to bootstrap an empty database); a backfilled account with no recorded role gets it filled once from GitHub on first use of its GitHub session. Only the 提督 can change site roles, in the console (`PATCH /api/console/people/:account_id/site-role`, which also needs `roles.manage`); the last admin cannot be demoted (409 `last_admin`); the change is audited (`identity_audit` `role_change`, `account.role`) and applies on the next request. A non-member keeps their titles for display but holds no capability. The console's GitHub organization pages (`/api/admin/:org/*`, only for `CONSOLE_ORG`, otherwise 403 `org_not_managed`) are executed by the server: with a GitHub App (`GH_APP_ID`, `GH_APP_PRIVATE_KEY`) through the App's installation token, otherwise through the caller's own GitHub session token, otherwise 409 `github_not_connected`. Residual risk: with an App, holders of `github.org.read` (in the default 舰员 bundle) read whatever the App can see, and holders of `github.*.manage` act as the App, which is what GitHub records; only the site audit says who did it. Leaving or being demoted in the GitHub organization no longer changes the site role; removal is done in the console. Making someone a GitHub owner, for example through the App by a holder of `github.members.manage`, does not make a site admin, except for a backfilled account whose role is still unrecorded, which is filled from GitHub on its first GitHub session. Before an App is configured, review the default bundles: the captain holds every capability (including deleting repositories and removing members) and the tech and projects heads hold `github.repos.manage`; these used to be capped by the person's own GitHub role.

Since #270 the server also embeds an OpenID Connect issuer at `<PUBLIC_ORIGIN>/oidc` (`oidc-provider` 9.12.2) so that apps on other origins, starting with the self-hosted GitLab, sign in with the site account. It offers the authorization-code flow only, with PKCE `S256` required for every client, exact redirect URIs on one host per client, single-use 10-minute codes (a replayed code revokes the grant and its tokens), and no dynamic registration, refresh tokens or single logout. The site `sid` decides who is signed in; non-members are sent back with `access_denied`, and userinfo answers 401 for an account that is disabled or no longer a member. A first sign-in to an app needs the person's consent on `/authorize`, accepted only from the account that started the login and audited as `oidc.consent` / `oidc.deny`. Each app gets its own random `sub` (pairwise by redirect host). The signing key `OIDC_JWKS` and the GitLab admin token `GITLAB_API_TOKEN` are environment secrets; clients are registered only through the server CLI, and their secrets are stored encrypted. With `GITLAB_SYNC=on` the server creates a GitLab user for every member, keyed by the OIDC identity, adds them to the group (Developer, Owner for 提督) and blocks those who leave; it never deletes users or repositories. Members who leave before they were ever synced but did sign in to GitLab are found by their OIDC identity and blocked too; the sync takes the sector from the registered `gitlab` client, not from `GITLAB_URL`, and does not follow redirects when calling GitLab. Protocol endpoints are rate-limited per IP with server-to-server calls (discovery, JWKS, token, revocation, userinfo: 600 a minute) counted apart from browser redirects (the authorization endpoint: 120 a minute). Residual risk: GitLab sessions already open are ended only by the next sync (up to 10 minutes, and only while `GITLAB_SYNC=on`; GitLab's single sign-on is to be switched on after the sync is), and the admin token gives full control of GitLab if leaked.

The console (`/api/console/*`) authorizes by site role plus title → capability, with no GitHub ceiling. Titles and departments are data: each title's label, tag, icon, tone, description and permission bundle live in the `titles` table, seeded once from the defaults in `app/server/src/lib/roles.ts` (`INSERT OR IGNORE`, so the database wins after the first start) and edited in the console through `PATCH /api/console/titles/:title_id` by whoever holds `roles.manage` (audited as `title.update`); the two top titles (提督 and 舰长) can only be edited by the 提督 (403 `admiral_required`), otherwise a 舰长 holding `roles.manage` could widen their own bundle. Only the title ids, their ranks, the capability list, the tone palette and the icon list are fixed in code. The default names follow the owner's starship scheme of 2026-09-25: 提督 (`admin`), 舰长 (`captain`), 队长 (`head`, shown as `{部门} · {label}`), 舰员 (`member`; `{部门} · {label}` inside a department), 领航员 (`alumni`), 乘客 (`guest`, not signed in, read-only). Site admins are the 提督 automatically and always hold every capability; the old bootstrap stand-in ("org admins act as captain until one is appointed") is gone. The server enforces that the 提督 bundle is always everything, the 乘客 bundle is always empty, and `roles.manage` fits only the 舰长 bundle. Only the 提督 or the current 舰长 can appoint or transfer the 舰长; the 舰长 row can be removed by the 舰长 themself or by the 提督. Deleting a department requires both `roles.manage` and the site admin role (提督); its heads and crew lose that department title in the same transaction (audited as `department.delete`), and the default departments are seeded only on the first start, so a deleted one does not come back after a restart. `GET /api/console/people` lists every site account with its site role, sign-in methods and titles, plus the GitHub organization members not yet signed in when GitHub is connected (holders of `roles.department.manage` see the whole list too, not just their department), and the anonymous `GET /api/public/org` publishes the display half of titles and departments (no bundles, no people) for the portal and the forum, which fall back to built-in defaults when it cannot be read. The forum backend (#57, `/api/forum/*` in the core server, [ADR-0004](../decisions/0004-forum-backend-in-core-server.md)) enforces the same `forum.*` capabilities server-side; guests may read and reply (proof of work, honeypot, per-IP limits with IPv6 counted per /64, a site-wide cap of 200 guest replies an hour, names limited to an allowlist of Han, common Latin letters, kana, Hangul, digits and a few separators) but not open topics, and a session whose account is no longer a member is treated as a guest. Every per-IP limit and every recorded client IP relies on `TRUST_PROXY=2` (the host nginx and the web container nginx), never on the client-supplied leftmost `X-Forwarded-For`.

Recruitment mail (#148) is queued in the `mail_outbox` table and sent by a worker inside the server process through Aliyun DirectMail, then Resend. A queued letter holds the recipient address and the rendered body (name, class, email, submission time, application id and, in the 已收到 letter, the strengths text) only while it is pending; once it is sent, abandoned after six attempts, or skipped (no provider configured, or not on the allowlist when allowlist mode is enabled), the address, HTML and text are set to NULL and only a SHA-256 of the address, the subject and the outcome remain. Error records and logs carry the provider name, HTTP status and the provider's error code, never credentials, addresses or bodies. Provider keys and the preview allowlist are environment secrets and stay empty in the repository. Because anyone can submit the public application form with someone else's address, abuse is stopped at the application itself rather than at the letter (#169, the owner's decision of 2026-09-27): one IP (IPv6 grouped by /64) and one device may each file at most five successful applications in a rolling 24 hours; the sixth gets 429 `apply_limited` and is neither stored nor mailed. The device is an httpOnly cookie that the apply endpoint sets for its own path only, so clearing cookies makes a new device and the IP is the real limit; the counter table `application_limits` keeps only SHA-256 hashes of the /64 or IP and of the device id, for at most 24 hours. Every stored application gets its 已收到 letter; the only cap left on letters is 200 per hour site-wide, so that someone rotating many IPs cannot use up the provider quota and block the official status letters. Domains ending in a dot, quoted local parts and IP literals are refused. The residual risk is five unsolicited letters per IP per day to arbitrary inboxes while Turnstile is off, and one inbox can get several letters from different IPs. Preview environment mails all applicants by default from #169 (`MAIL_RECIPIENTS=all`), so testing applications or status reviews on preview sends real emails containing `prev.yangtzeu.work` links to real candidate addresses. People behind one shared exit (a campus network, a dormitory, a hotspot, or one IPv6 /64) share the per-IP count: the 6th applicant in a day is refused with a message and can apply the next day. Console status changes carry the status and the review version the reviewer saw (`expected_status`, `expected_review_id`, the largest review id, which only grows even if the server clock steps back); a stale change, including a status changed away and back, gets 409 and sends nothing, and a status change without both fields (an old page) is refused too.

Contest rehearsal (#276, 2026-10-27): see the [finite matrix](../services/server/competition-rehearsal.md) for verified routes and outstanding identity integration. Self-review is refused for manual scores and revocations too. Portal competition writes and activity records commit together. Finalization freezes signups/settings and both ladders; participant cursors contain a contest-specific digest, not an encoded account ID. Incomplete GitLab collection never applies a partial round or revokes existing points. This is not browser or production acceptance.
