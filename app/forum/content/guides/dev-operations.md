这篇写日常排查问题时常用的几个入口和几类常见故障。

1. 健康检查：两个环境都能查 `/healthz`（经 web 容器反代到 server），正常时返回 HTTP 200 且 `{ "ok": true }`；部署脚本用它做上线前的健康门，默认轮询 180 秒。
2. 发布身份核对：web 容器内置的 `/release.json`（`Cache-Control: no-store`）记着这次构建的环境、版本号和提交，应该和目标机 `.env.<环境>` 里的 `IMAGE_TAG`、`docker inspect` 查出来的镜像 digest 对得上；对不上说明发布流程哪一步出了问题。
3. 查日志：在目标机的栈根目录用

```
docker compose --env-file .env.<环境> -f deploy/compose/<环境>.yml logs <服务名>
```

服务名是 `server`、`web`、`forum` 三个之一；部署历史另外记在栈根目录的 `deploy-history.log`，一行记一次部署或回滚的结果。
4. 静态资源走 CDN（七牛）时，带内容哈希的构建产物（脚本、样式、字体、图片）从 CDN 加载，源站上这些文件仍然在，只是页面不优先用它们；CDN 出问题时关掉上传的权限，重新发一次预发布版本就会切回同源加载，已经上线的镜像不会自己切回去。
5. 常见故障：
   - `/healthz` 一直超时：先看对应的容器是不是在跑，再看目标机能不能正常访问数据卷所在的磁盘；
   - 页面能打开但接口 404 或者 502：大概率是反代规则或者某个容器没启动，核对服务名和依赖关系；
   - 发布之后样式或脚本加载不出来：先看是不是开着静态资源 CDN、CDN 那边的白名单有没有包含当前域名；
   - 登录失败回到登录页并带了失败原因：原因本身就是枚举值（连不上第三方登录、不是组织成员、取消了授权、账号已停用），不是程序出错。
6. 怀疑是环境差异导致的问题，先核对两个环境是不是真的保持同构（宿主 nginx 配置、CDN 白名单、第三方登录回调地址）：环境不同构是「预发布正常、正式环境出问题」最常见的原因，细节见《发布与部署》（./t920）。
