这篇写现在实际怎么从一个想法走到代码合并，按顺序做就不会漏步骤。

1. 改动前先确认要不要做：查一遍有没有重复的 issue，按「痛点／解决方案／最终效果与验收条件」把事情写清楚，等负责人明确批准具体事项之后才建立 issue；没确认之前不建分支、不动手改。
2. 建一个 task 分支和独立的工作目录：

```
node scripts/task.mjs start <issue编号> <简短的英文标识>
```

它会从最新的 `stage` 拉出 `task/<issue>/<标识>` 分支，建一个独立的 git worktree，并在 issue 上留一条「开工」记录。运行前先设好身份（`GEEK_NOTES_USER`、`GEEK_NOTES_BY`），之后这件事的全部编辑、安装、构建、测试、提交都在这个 worktree 里做，不在主工作区切分支，也不在一个 worktree 里同时做两件事。
3. 开发过程中每完成一步（提交、推送、开合并请求、收到审查结论、返工）都记一条执行记录：

```
node scripts/note.mjs add --stage 提交 --issue <issue编号> \
  --title "一句话" --did "做了什么" --result "命令的真实输出摘要"
```

记录和代码一起提交进仓库，落在 `notes/<日期>/<用户名>/<链路>.md`。
4. 提交信息用固定格式：`<type>(<scope>): <中文简述>`，一次提交一个可以独立回滚的目的，例如 `fix(forum): 防止重复删除回帖破坏统计计数`。不写 `update`、`WIP` 这类没有信息量的消息。
5. 本地跑完相关的检查（至少 `pnpm verify`，涉及浏览器行为再跑 `pnpm test:e2e`）之后推送分支，在自建代码托管平台上开一个指向 `stage` 的合并请求（MR）。正文按模板写满必须的段落：目的、关联（写 `Closes #<issue>`）、变更范围、宏观对齐、解决链路、验证命令与结果、验收证据、人工验收步骤、审查结论、风险与回滚，缺一个都不行。
6. 请人按审查清单逐条过一遍改动，把结论写进 MR：通过、有条件通过、阻塞，三种之一；没有审查结论的 MR 不允许合并。按审查意见改完后补一条「审查」执行记录再推。
7. 合并只用合并提交，不要用压缩合并或者变基合并——文档同步检查是按提交时间先后比较代码改动和对应文档改动的，换一种合并方式这个顺序会乱。
8. 合并之后当场核对：这个 MR `Closes` 的 issue 必须关闭并留一条「关闭」记录，远端的 task 分支必须删除；自动化没处理到的由合并的人手工补齐。
9. 本机收尾：

```
node scripts/task.mjs finish <issue编号>
```

在主工作区运行，删掉这个 worktree 和本地分支，并写下「收尾」记录，一条链路到这里才算完整。本机如果还留着已经合并或者 issue 已关但没 `finish` 的 worktree，推送会被本地的 pre-push 钩子拦住，提示该清理哪些。
